Seed Repo Release and Version History
==============================================================================
The changelog of this **seed repo** itself. The seed is a runnable project that `cookiecutter-aws_lbd <https://github.com/MacHu-GWU/cookiecutter-aws_lbd>`_ (the template repo) turns into a cookiecutter template, so every change here is a change to what newly generated projects get.

- The seed and the template repo share one version number. The source is ``version`` in this repo's ``pyproject.toml``; the template repo copies it and refuses to publish when the two differ.
- ``release-history.rst`` is template content: the starting changelog of every generated project. It never records the seed's own changes, and is never edited for a seed release.
- This file is excluded from the template. Each template release links to its section here.

1.0.0 (2026-10-23)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
First release recorded in this file. The version jumps from ``0.2.1`` to ``1.0.0`` because the seed and the template repo now share one version number (both were ``0.2.1``), and the shared version starts at a new major. Nothing generated projects receive is incompatible with ``0.2.1``, except the starting changelog (see Minor Improvements). This section describes everything a project generated from this seed gets.

**Features and Improvements**

- **Multi-environment AWS Lambda code base in Python:** workload environments ``dev``, ``tst``, ``prd``, selected by ``ENV_NAME``, plus a ``devops`` environment that owns the shared Lambda layer and its artifacts bucket
- **Runtime and environment detection:** ``runtime.py`` tells where the code runs, ``env.py`` which environment it targets
- **Config:** one pydantic ``Config``, loaded from ``config/config-{shared,<env>}{,-secret}.json5`` on a developer machine and from an SSM SecureString parameter in Lambda; the ``-secret`` files, which hold the account IDs, are git-ignored. ``mise run config-deploy-<env>`` / ``config-delete-<env>`` write the config to SSM only when it changed, and a config change redeploys the functions through a config hash in the template
- **One singleton:** ``one``, the single entry point to the runtime, the environment, the config, and the boto sessions (``one.bsm`` and ``one.bsm_devops``)
- **Lambda functions:** pydantic ``BaseInput`` / ``BaseOutput`` classes that validate the event, run ``main()`` locally or in Lambda, and serialize the result, with two sample functions (``hello`` and the S3-triggered ``s3sync``)
- **Lambda layer:** built from ``[project] dependencies`` and ``uv.lock`` with uv for Linux, without Docker; published once in the devops account only when ``uv.lock`` changed, granted to every workload account, and pinned per environment with ``lambda_layer_version``. ``mise run lambda-layer-check-<env>`` runs before every deploy; ``lambda-layer-cleanup`` / ``lambda-layer-cleanup-real-run`` keep the latest 3 versions and every pinned one
- **Lambda source:** the function code ships as the package's source files (``mise run lambda-source-build``), so an unchanged code base is not redeployed
- **CDK:** two stacks per environment, ``infra`` (the Lambda execution role) and ``lbd`` (the functions, the layer, and the S3 trigger), ``StackCtxEnum`` / ``StackEnum``, and ``infra_stack_exports.py`` / ``lbd_stack_exports.py`` that other projects copy to read the stack outputs
- **One command per stack:** ``cdk-{synth,plan,up,down}-<env>-*`` mise tasks, generated by ``mise run cdk-gen-tasks``; every ``cdk-up`` task builds the source, checks the layer, and deploys the config first. ``mise run print-cdk-stack-urls`` prints the console link of every stack
- **Quick links:** ``QUICK_LINKS.md``, the console URL of every AWS resource by environment, generated by ``mise run gen-quick-links``
- **Tests:** unit tests synthesize the stacks without calling AWS; integration tests (``tests_int/``, ``mise run int-test``) invoke the deployed functions and check the stack exports
- **Tools pinned by mise:** Python, Node.js, the AWS CLI, and the cdk CLI (``npm:aws-cdk``), plus ``.env`` loaded for every task
- **Python tooling:** Python 3.12 (``requires-python = ">=3.12,<3.13"``, the Lambda runtime), uv with a committed ``uv.lock`` and exported ``requirements*.txt``, ruff format and lint with a one-imported-name-per-statement check, pytest with coverage, Sphinx docs on Read the Docs, and GitHub Actions CI
- **Release:** ``mise run release`` creates the GitHub tag and release; the project is not published to PyPI
- **AI ready:** ``CLAUDE.md`` with the first-time setup, the deploy flow, and the common tasks, and Claude Code skills: ``pywf-aws-lbd-base`` (the Lambda and CDK project conventions, every link pinned to this repo's tag of the template version), the API skills of the libraries it builds on (``aws_lbd_art_builder_core``, ``aws_lbd_art_builder_uv``, ``boto_session_manager``, ``cdk_mate``, ``s3pathlib``, ``simple_aws_ssm_parameter_store``), ``aws-cdk-cli-ref``, and the ``pywf-oss-*`` family for the Python tooling

**Minor Improvements**

- A generated project's ``release-history.rst`` now starts empty (the Backlog and a ``0.1.1`` first release), like every pywf template. In ``0.2.1`` it also carried the template's own ``0.2.1`` release notes, which describe the template, not the generated project; they moved to the ``0.2.1`` section of this file

**Miscellaneous**

- The links and the version in ``pywf-aws-lbd-base`` now point to ``1.0.0``. In ``0.2.1`` they pointed to a ``0.2.1`` tag of this repo that was never created
- New ``release-history-seed-repo.rst`` (this file) and the seed-only ``pywf-oss-changelog-seed-repo`` skill that maintains it; both stay out of the template


0.2.1 (2026-10-21)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
**Breaking Changes**

- Rebuild the template on the pywf AWS CDK template, for several environments instead of one: workload environments ``dev``, ``tst``, ``prd``, selected by ``ENV_NAME``, plus a ``devops`` environment that owns the shared Lambda layer and its artifacts bucket.
- Replace ``.env.shared`` and the Lambda environment variables with one pydantic ``Config``, loaded from ``config/config-{shared,<env>}{,-secret}.json5`` on a developer machine and from an SSM SecureString parameter in Lambda. The ``-secret`` files, which hold the account IDs, are git-ignored.
- Split the infrastructure into two CDK stacks per environment: ``infra`` (the Lambda execution role) and ``lbd`` (the functions, the layer, and the S3 trigger).

**Features and Improvements**

- Add ``one``, the single entry point to the runtime, the environment, the config, and the boto sessions (``one.bsm`` and ``one.bsm_devops``).
- Build the Lambda layer from ``[project] dependencies`` and ``uv.lock`` with uv for Linux, without Docker; publish it once in the devops account only when ``uv.lock`` changed, grant every workload account, and pin a version per environment with ``lambda_layer_version``.
- Add ``mise run lambda-layer-check-<env>``, run before every deploy, and ``mise run lambda-layer-cleanup`` / ``lambda-layer-cleanup-real-run``, which keep the latest 3 versions and every pinned one.
- Deploy the function code as the package's source files (``mise run lambda-source-build``), so an unchanged code base is not redeployed.
- Add ``mise run config-deploy-<env>`` / ``config-delete-<env>``, which write the config to SSM only when it changed. A config change now redeploys the functions, through a config hash in the template.
- Generate the per-environment ``cdk-{synth,plan,up,down}-<env>-*`` tasks with ``mise run cdk-gen-tasks``. Every ``cdk-up`` task builds the source, checks the layer, and deploys the config first.
- Add ``QUICK_LINKS.md``, the console URL of every AWS resource by environment, generated by ``mise run gen-quick-links``.
- Add ``infra_stack_exports.py`` and ``lbd_stack_exports.py``, which other projects copy to read the stack outputs.

**Miscellaneous**

- Rewrite ``README.rst`` and ``CLAUDE.md`` with the first-time setup, the deploy flow, and the common tasks; every task that writes to AWS says so in its description.
- Add the ``pywf-aws-lbd-base`` Agent Skill, which holds the conventions of the project.
- Remove the Maintainer Guide from the docs, and the ``setup-codecov`` and ``setup-readthedocs`` tasks.
